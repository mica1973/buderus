# EDS / DA / Experience Workspace / EMA — Initial Working Knowledge

This is the baseline for polishing sites migrated by Adobe's Experience Modernization Agent (EMA) to Edge Delivery Services (EDS). Reviewed against Adobe documentation on 2026-10-23. “EDS” means Edge Delivery Services, not AEM Sites JCR/OSGi or CDN edge compute; current primary docs override any older repo note.

## Architecture and content model

- An EDS site binds a **code source** and a **content source** as distinct configuration. The common project uses GitHub for code and DA/document authoring for content; they need not be the same provider. Code previews use `https://{branch}--{site}--{org}.aem.page/{path}`. `.aem.live` is the EDS live environment, not necessarily the customer's final production hostname. Sources: [project anatomy](https://www.aem.live/developer/anatomy-of-a-project.md), [developer tutorial](https://www.aem.live/developer/tutorial.md), [authoring](https://www.aem.live/docs/authoring.md), [Sidekick](https://www.aem.live/docs/sidekick.md).
- Typical EDS code is buildless HTML/CSS/JavaScript modules. Canonical page content is server-delivered; client code decorates and enhances it. Eager/Lazy/Delayed loading phases protect the critical path. Source: [project anatomy](https://www.aem.live/developer/anatomy-of-a-project.md), [Keeping it 100](https://www.aem.live/developer/keeping-it-100.md).
- Prefer semantic default content for headings, prose, lists, links, and images; use blocks for structured/repeated/interactive patterns. Sections are document-level containers. In supported authoring formats, horizontal rules divide sections; a block is represented by a table whose first/merged row identifies the block and later row(s) contain authored content. Authors author the table, not the final decorated DOM. Sources: [sections and blocks](https://www.aem.live/developer/markup-sections-blocks.md), [EW editing documents](https://www.aem.live/docs/ew/authoring/editing-docs), [block collection](https://www.aem.live/developer/block-collection.md).
- The first block class token names the block; runtime adds `.block`, `.<name>-wrapper`, and `.<name>-container` classes. Page `metadata` is distinct from section metadata such as `style`, and `template`/`theme` page metadata can become body classes. Keep blocks un-nested, CSS scoped to `.<blockname>`, and decoration tolerant of authors omitting/adding cells. Inspect `http://localhost:3000/{path}.plain.html` (or `.md`) before block work; never edit vendored `scripts/aem.js`. Sources: [sections and blocks](https://www.aem.live/developer/markup-sections-blocks.md), [page metadata](https://www.aem.live/docs/metadata.md), [AI coding agents](https://www.aem.live/developer/ai-coding-agents.md), [boilerplate runtime](https://github.com/adobe/aem-boilerplate/blob/main/scripts/aem.js).
- The inspected [AEM block collection](https://github.com/adobe/aem-block-collection/tree/main/blocks) has 16 block folders but no per-block `README.md`/`metadata.json` authoring schemas. Code-derived patterns include cards converting rows to list items, accordion rows to `<details>`, tab rows to labels/panels, and table rows to semantic `<thead>/<tbody>`; treat them as examples and validate actual `.plain.html` before reusing any block contract.

## DA / Experience Workspace and configuration

- Document Authoring (DA), now Experience Workspace (EW), is an EDS-oriented document authoring surface; EW is an evolution of DA, not a migration of code/content. Documents contain body content and block structures; sheets manage structured data such as metadata, placeholders, redirects, and configuration. Sources: [EW overview](https://www.aem.live/docs/ew/about), [DA is now EW](https://www.aem.live/docs/ew/da-is-ew), [editing sheets](https://www.aem.live/docs/ew/authoring/editing-sheets), [spreadsheets](https://www.aem.live/developer/spreadsheets.md), [placeholders](https://www.aem.live/docs/placeholders.md), [redirects](https://www.aem.live/docs/redirects.md).
- Keep DA Source/content APIs (files, media, versions, DA config) separate from EDS Admin Service/Admin API (site/delivery config and operations); authoring ACLs are a further layer. DA API examples use IMS bearer auth; EDS Admin APIs have their own auth/permissions. A DA source write does not automatically preview or publish. Preview is for review; publish is production-facing. Sources: [DA Source API](https://docs.da.live/developers/api/source), [DA API headers](https://docs.da.live/fragments/api/headers), [EW permissions](https://www.aem.live/docs/ew/administering/permissions), [EW publishing](https://www.aem.live/docs/ew/authoring/publishing), [AEM Admin API](https://www.aem.live/docs/admin.html).
- EDS code/content bindings live in the Configuration Service/Admin Service (UI: [tools.aem.live](https://tools.aem.live/)); EW org/site authoring settings are separate and can inherit/override. Do not create new site setup with `fstab.yaml`, `helix-query.yaml`, or `paths.json`; legacy projects may still contain these. Verify actual `contentSourceUrl` only after exact org/site are known. Sources: [Configuration Service](https://www.aem.live/docs/config-service-setup.md), [EW configs](https://www.aem.live/docs/ew/administering/configs). The bootstrap's [DA Admin API landing URL](https://opensource.adobe.com/da-admin/) returned HTTP 404 in this review; current docs.da.live API pages were reachable.

## EMA output and quality bar

- EMA documentation covers site analysis/cataloging, prompting, templates/blocks, generated import support, preview/review, and code changes. Catalog output may include an HTML report bundle and JSON page/template/block inventories; the catalog skill requires a publicly accessible site and may miss interaction-dependent content. Treat artifacts as tool-specific evidence, not assumed output. Sources: [EMA overview](https://experienceleague.adobe.com/en/docs/experience-manager-cloud-service/content/ai-in-aem/agents/brand-experience/modernization/overview), [getting started](https://experienceleague.adobe.com/en/docs/experience-manager-cloud-service/content/ai-in-aem/agents/brand-experience/modernization/getting-started), [prompting guide](https://experienceleague.adobe.com/en/docs/experience-manager-cloud-service/content/ai-in-aem/agents/brand-experience/modernization/prompting-guide), [site catalog](https://experienceleague.adobe.com/en/docs/experience-manager-cloud-service/content/ai-in-aem/agents/brand-experience/modernization/site-catalog), [Adobe migration article](https://blog.developer.adobe.com/en/publish/2026/03/how-the-experience-modernization-agent-migrates-sites-to-edge-delivery-services).
- Review generated output on the actual site: check author-facing variation names, duplicate blocks, global/unscoped CSS, importer residue, old-domain links, metadata/nav/footer/404/redirect coverage, accessibility and media. Do not claim Lighthouse 100 without measuring. Prioritize first-section/LCP resources; defer non-critical scripts and later content. Avoid speculative preloads/preconnects/third parties; measure mobile and desktop. Sources: [Keeping it 100](https://www.aem.live/developer/keeping-it-100.md), [go-live checklist](https://www.aem.live/docs/go-live-checklist.md), [development collaboration](https://www.aem.live/docs/dev-collab-and-good-practices.md).

## Safe working loop

1. Confirm exact EDS preview/repo and DA source. Before any EMA tool besides `get_current_site`, call `get_current_site` and verify the loaded target.
2. Inventory code/config/content and inspect representative `.plain.html`; model blocks from actual authoring markup.
3. Make narrow code changes on a feature branch, never `scripts/aem.js`; validate in the proxy/browser at desktop and mobile, lint, and run PSI/Lighthouse when available.
4. Use a PR with its branch `.aem.page` preview URL. Keep DA preview/publish separate; publish, unpublish, delete/overwrite, push code/content, or change config only on the user's explicit go. Report only checks actually run.
